# 낙상 감지 데이터 전처리 — 상세 기록

이 문서는 AIHub 163 키포인트 라벨을 ST-GCN류 시계열 분류기(현재 HD-GCN 채택,
아래 참고) 학습용 데이터로 변환하는 전체 과정을 상세히 기록한다. 보고서 작성용이므로
"무엇을 했는지"뿐 아니라 "왜 그렇게 했는지"와 "무엇이 잘못됐고 어떻게 고쳤는지"를
시간 순서대로 남긴다.

## 0. 원본 데이터 형식

AIHub 163(공사현장 안전장비 인식 데이터)의 키포인트 라벨은 4개 카테고리 zip으로
제공된다: `1.떨어짐.zip`(falling_from_height), `2.부딪힘.zip`(struck_by_collision),
`3.넘어짐.zip`(trip_and_fall), `4.물체에_맞음.zip`(struck_by_object). 각 zip 안에는
JSON 파일이 프레임 하나당 하나씩 들어있다:

```json
{
  "image": {
    "date": "20201207",
    "path": "S2-N4601M00001",
    "filename": "S2-N4601M00103.jpg",
    "resolution": [1920, 1080]
  },
  "annotations": [
    {
      "data ID": "S2",
      "middle classification": "08",
      "class": "46",
      "point": [[x1,y1,v1], [x2,y2,v2], ..., 16개]
    }
  ]
}
```

**확인된 사실**:
- `annotations` 리스트 길이는 항상 1이다(5000개 샘플 확인) — 프레임당 한 사람만
  라벨링되어 있어, "여러 사람의 keypoint가 섞이는" 문제는 없다.
- `image.path`는 원본 영상(촬영 세션) ID다. 같은 `path`를 공유하는 모든 프레임은
  같은 영상에서 나온 것이다.
- `annotations[0]["class"]`, `["middle classification"]`은 **같은 path 내에서
  항상 같은 값**이다(예: S2-N4601M00001은 항상 `("08","46")`) — 즉 이 필드는
  "지금 이 프레임에서 무슨 동작을 하고 있는지"가 아니라 **영상/세션 단위 식별자**다.
  프레임 단위로 동작 국면(서 있음/넘어지는 중/누워있음)을 구분하는 필드는
  **JSON 어디에도 없다.** 이 사실이 아래 v1의 핵심 한계로 이어진다.
- keypoint는 COCO-17이 아니라 **16개 점**이다. 각 점이 해부학적으로 무엇을
  의미하는지(어깨/팔꿈치/무릎 등) 알려주는 AIHub 공식 가이드 문서를 확보하지
  못해, 실제 이미지에 점을 찍어 눈으로 확인하는 방식으로 best-effort 매핑을
  추론했다. 상세 내용과 신뢰도 한계는 `docs/keypoint_mapping.md` 참고
  (2프레임만 교차검증한 상태로 확정 아님).

## 1. 전수 분석 (`scripts/analyze_keypoint_labels.py`)

4개 카테고리 train 라벨 전체(95,798개 파일)를 zip에서 직접(압축 해제 없이)
읽어 `path`별로 그룹핑하고 프레임 번호 간격을 분석했다.

| 카테고리 | 파일 수 | 영상 그룹 수 | 그룹 크기(최소/중앙값/최대) | 프레임 간격(최소/중앙값/최대) |
|---|---|---|---|---|
| falling_from_height | 23,840 | 7 | 14 / 3986 / 4039 | 1 / 1 / 12 |
| struck_by_collision | 23,990 | 8 | 1479 / 3002 / 4011 | 1 / 1 / 6 |
| trip_and_fall | 23,899 | 7 | 3145 / 3410 / 3666 | 1 / 1 / 7 |
| struck_by_object | 24,069 | 10 | 831 / 2041 / 6929 | 1 / 1 / 7 |

**주의**: 이 분석은 처음에 validation 셋의 작은 서브셋 하나(443프레임, path 1개)만
보고 "프레임 간격이 불균일(중앙값 7, 최대 60)"하다고 잘못 결론 내렸던 것을,
train 셋 전체를 전수 분석해 정정한 결과다. train 셋은 간격 중앙값이 1이다.

**그런데 중앙값 1이 "거의 연속"을 의미하지 않는다** — 아래 2절 참고.

## 2. v1: 기계적 슬라이딩 윈도우 (`scripts/convert_aihub163_keypoints_to_pyskl.py`)

### 2.1 문제: gap=1(끊김 허용 0) 기준으로는 극심하게 파편화됨

프레임 간격의 **중앙값**이 1이라고 해서 "끊김이 거의 없다"는 뜻이 아니었다.
`max_gap_for_continuity=1`(정확히 연속된 프레임만 하나의 run으로 인정)로
falling_from_height의 실제 연속 구간(run) 길이 분포를 뽑아보니:

```
n_runs=4795, min=1, p25=2, median=4, p75=7, p90=11, max=38
n_runs >= 10: 661 (14%)   n_runs >= 15: 190 (4%)   n_runs >= 20: 61 (1%)
```

그룹 하나에 프레임이 최대 4000개 가까이 있는데도, 실제로 **끊김 없이 이어지는
구간은 median 4프레임**에 불과했다. 즉 사람이 프레임에서 2~3프레임씩 잠깐씩
사라지는 일이 매우 잦다(Phase 1에서 확인한 "쓰러진 자세를 탐지기가 놓친다"는
문제와 같은 원인일 가능성 — 라벨링 파이프라인도 사람을 확신 있게 찾은 프레임만
keypoint를 남겼을 것으로 추정).

**결과**: `window_length=30` 조건을 만족하는 run이 카테고리별로 영상 그룹 수와
거의 같은 7~10개뿐이라, **전체 4개 카테고리를 합쳐 윈도우 30개**만 생성됐다.
학습에 쓰기엔 턱없이 부족했다.

### 2.2 해결: gap-bridging 보간

끊김 허용치(`max_gap_for_continuity`)를 1/3/5/10으로 바꿔가며 run 길이 분포를
다시 실측 비교했다:

| max_gap | n_runs | median | p90 | max |
|---|---|---|---|---|
| 1 | 4795 | 4 | 11 | 38 |
| **3** | 224 | **61** | 269 | 681 |
| 5 | 30 | 28 | 3723 | 4039 |
| 10 | 9 | 3950 | 4039 | 4039 |

gap=5부터는 run 하나가 거의 영상 전체(4000프레임)를 이어붙이기 시작해 실제
장면 전환(다른 반복 시연, 카메라 컷 등)까지 하나의 run으로 취급할 위험이 커진다.
**gap=3을 채택**했다: median 런 길이가 4→61프레임으로 크게 늘면서도, 여전히
장면 전환으로 보이는 큰 끊김(gap>3)은 분리한다.

gap≤3인 짧은 끊김은 버리지 않고 **양 옆 실측 프레임을 선형 보간**해서 채운다
(`densify_run` 함수). 보간된 프레임은 `keypoint_score`(원래 AIHub visibility
채널)를 0으로 덮어써서, 학습 코드가 "이건 실측이 아니라 보간값"이라고 구분할
수 있게 했다.

### 2.3 v1 최종 결과

`window_length=30`, `window_stride=15`, `max_gap_for_continuity=3`:

| 카테고리 | 영상 그룹 수 | 생성된 윈도우 수 |
|---|---|---|
| falling_from_height | 7 | 1663 |
| struck_by_collision | 8 | 1698 |
| trip_and_fall | 7 | 1647 |
| struck_by_object | 10 | 1679 |
| **합계** | 32 | **6687** |

`pyskl` `PoseDataset` 포맷(`frame_dir`, `label`, `img_shape`, `original_shape`,
`total_frames`, `keypoint` (M,T,V,C), `keypoint_score` (M,T,V)) 요구사항을
충족하는지 실제로 pickle을 다시 로드해 shape과 클래스 분포까지 확인했다.

### 2.4 v1의 근본 한계 (사용자 지적, 2026-07-06)

v1은 "영상 하나 = 하나의 카테고리 라벨"을 그 영상에서 잘라낸 **모든** 윈도우에
그대로 적용한다. 그런데 실제로 영상 하나(예: S2-N4601M00001, 3995프레임)의
keypoint bbox 종횡비(가로/세로 — 서 있으면 작고 누우면 큼)를 프레임 순서대로
10구간으로 나눠 평균을 보면:

```
구간0: 0.96  구간1: 0.83  구간2: 0.94  구간3: 1.00  구간4: 0.83
구간5: 0.86  구간6: 0.87  구간7: 0.90  구간8: 1.00  구간9: 0.90
```

영상 전체에 걸쳐 값이 고르게 섞여 있고, "누움"(ratio>1.3)으로 볼 수 있는 프레임은
**전체의 18.3%뿐**이다. 즉 이 ~4000프레임짜리 영상 하나에 낙상 동작이 여러 번
반복 시연되고, 나머지 대부분은 그냥 서 있거나 회복하는 구간이다. 그런데 라벨
JSON에는 "지금 이 프레임이 낙상 동작 중인지"를 알려주는 필드가 전혀 없다(0절
참고). **즉 v1이 만든 6687개 윈도우 중 상당수는 실제로 "가만히 서 있는 모습"인데
"낙상" 카테고리로 잘못 라벨링됐을 가능성이 높다.** 이것이 v2를 만든 직접적인
이유다.

## 3. v2: 전환 감지 기반 윈도우 (`scripts/convert_aihub163_keypoints_to_pyskl_transition.py`)

v1은 그대로 남겨뒀다(사용자 요청 — 나중에 v1/v2를 실제 분류기 학습 성능으로
비교하는 ablation을 진행할 계획).

### 3.1 아이디어

Stage A 휴리스틱(`src/fall_detection/heuristic_trigger.py`)에서 이미 "bbox
종횡비가 짧은 시간에 급격히 커지면 낙상 후보"라는 규칙을 만들어뒀다. 이 규칙을
**그대로, 정답 keypoint 시퀀스에** 적용하면, 사람이 직접 프레임 단위로 라벨링해
주지 않은 "실제 전환 순간"을 휴리스틱으로 근사할 수 있다.

- 각 run(2.2절의 gap-bridging 보간 재사용)에서 프레임별 keypoint bbox 종횡비
  `ratio(t)`를 계산.
- `ratio(t) - ratio(t - window_frames)` (Stage A와 동일하게 `window_frames=15`)가
  `aspect_ratio_delta_threshold`(Stage A와 동일하게 `0.5`) 이상이면 "전환 후보".
  연속된 후보는 하나의 이벤트로 묶어 중앙 프레임을 대표로 삼는다.
- 전환 지점 중심으로 `window_length`(30)프레임을 **양성(해당 카테고리)** 윈도우로
  추출.
- 전환 지점에서 `negative_exclusion_margin`(45프레임) 이상 떨어진 구간에서
  **음성("normal", 낙상 아님)** 윈도우를 최대 `max_negatives_per_run`(20개/run)
  추출 — 지금까지 4개 카테고리가 전부 "이상행동"이라 정상 데이터가 아예 없었는데,
  이 방식의 부산물로 확보된다.

### 3.2 v2 실측 결과

| 카테고리 | 검출된 전환 수 | 양성 윈도우 | 음성(normal) 윈도우 |
|---|---|---|---|
| falling_from_height | 581 | 581 | 34 |
| struck_by_collision | 164 | 164 | 559 |
| trip_and_fall | 568 | 568 | 49 |
| struck_by_object | 193 | 193 | 567 |
| **합계** | 1506 | **1506** | **1209** |

총 2715개 윈도우 (`data/processed/fall_keypoints_transition/train_windows_transition.pkl`).

### 3.3 v2의 한계 — 카테고리별 검출 편향

falling_from_height/trip_and_fall은 전환이 500건 이상 검출된 반면
struck_by_collision/struck_by_object는 164~193건뿐이다. "종횡비가 급격히
커진다(서 있다가 눕는다)"는 신호가 낙상·넘어짐에는 잘 들어맞지만, 부딪힘·물체에
맞음은 맞고 휘청이거나 웅크리는 정도로 끝나 눕는 자세까지 안 갈 수 있어 이
신호로는 잘 검출되지 않을 수 있다. **즉 v2도 완벽하지 않고 카테고리에 따라
재현율(recall)이 다를 수 있다** — 사람이 직접 라벨링한 정답 전환 시점이 아니라
휴리스틱 추정치이기 때문이다.

## 4. v1 vs v2 비교 요약

| | v1(기계적 슬라이딩) | v2(전환 감지) |
|---|---|---|
| 라벨 정확도 | 낮음 — 대부분 "서 있는 모습"에 낙상 라벨 오염 가능 | 상대적으로 높음 — 실제 전환 주변만 양성으로 라벨 |
| 데이터 양 | 많음(6687개) | 적음(2715개, 그중 양성은 1506개) |
| 정상(normal) 클래스 | 없음 | 있음(1209개) |
| 카테고리별 편향 | 없음(그룹 크기에 비례) | 있음(낙상·넘어짐에 유리, 부딪힘류에 불리) |

**다운스트림 분류기(HD-GCN) 학습 성능으로 실제 비교(ablation)는 아직 미실시** —
사용자가 시간 여유가 될 때 진행하기로 함.
